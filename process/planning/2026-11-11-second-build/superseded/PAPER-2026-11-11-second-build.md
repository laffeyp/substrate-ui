# Working inside Substrate: a second build beside the one in use

*2026-11-11. Prior work, the conflicts measured or read in the code, a design, and three experiments. Asked for by the Architect on 2026-11-11 (BLACKBOARD, the last `user` entry of that date): "there needs to be an additional final build stage … the one that we are working inside of … We can hot swap it out whenever we want", "work out whether or not that will have any conflicts", with the prior work "literally in the domain of software engineering".*

## Abstract

Substrate is to be built from inside Substrate. That needs two installs on one machine: the one the work happens in, and the one under test. Rust and GCC keep a known-good compiler in use while they build the next and compare stages; VS Code, Chrome and Eclipse give the second install its own name and data; blue-green deployment keeps the old build installed for rollback and warns that shared data is the hard part; Thompson showed what a tool can slip into what it builds, and Wheeler how to catch it. On today's code, a second install conflicts with the first in four places. Two are seen on this machine: same-named installs share one single-instance lock, and a test server run from a session writes into the working app's live trace. Two are read in the code: both backends load and end each other's sessions in a shared store, and the runbook's install step quits the app doing the installing. The design gives the test install its own name, bundle id, store and logs, all fixed at build time. The swap runs outside the app it replaces. The vocabulary gains one boot field so a trace says which install wrote it. The experiment worth running is Wheeler's diverse double-compiling, in Substrate's terms: build one commit from a plain terminal and from a session inside the working install, and compare the two bundles.

## 1. Prior work

### Compilers built by themselves

Rust builds in stages. Stage 0 is "the pre-compiled compiler and standard library", a downloaded beta. Stage 1 is the current source compiled by stage 0. Stage 2 is the source compiled by stage 1, and "the `stage2` compiler is the one distributed with `rustup`". Stage 1 is not shipped because "the ABI generated by the stage0 compiler may not match the ABI that would have been made by the stage1 compiler" (rustc-dev-guide). GCC's default `make` is "a full three-stage bootstrap", and `make compare` "compares the results of stages 2 and 3", because the compiler "should produce the same object files regardless of how it itself was compiled" (GCC internals, Makefile targets). Both keep the tool in use fixed while the next one is made, and GCC's compare turns "it built" into a check.

Thompson's Turing lecture (CACM 27(8), August 1984, 761–763) plants a Trojan horse in the C compiler that reinserts itself whenever the compiler compiles its own source, then removes it from the source: "the login command will remain bugged with no trace in source anywhere." His moral: "No amount of source-level verification or scrutiny will protect you from using untrusted code." Wheeler's counter-measure, diverse double-compiling (PhD dissertation, George Mason University, 2009), compiles the compiler's source "once with a second (trusted) compiler", then compiles the source again with that result. If the output "is bit-for-bit identical with the untrusted executable", then "the source code accurately represents the executable". A build made inside a tool can carry the tool's influence. A second, independent build of the same source finds it.

### Two installs side by side

VS Code Insiders "installs side by side" with Stable and "has isolated settings, configurations, and extensions" (VS Code FAQ). Chrome gives each channel its own data folder, `~/Library/Application Support/Google/Chrome` and `…/Chrome Canary` on macOS, and "two running Chrome instances cannot share the same user data directory" (Chromium, `docs/user_data_dir.md`). Eclipse's plug-in tools run the plug-in under development in a second Eclipse, the runtime workbench, whose workspace "must, of course, be different than the location of your host workspace" (Eclipse PDE, Eclipse Application launcher, Main tab). In all three, the second install is a different app to the operating system, with its own data.

### Hot swap

Blue-green deployment keeps "two production environments, as identical as possible", one live and one idle; rollback is "switch the router back". "Databases can often be a challenge with this technique": the remedy is to first "change the schema to support both the new and old version of the application" (Fowler, BlueGreenDeployment). The swap is cheap while the old build stays installed. The data both builds read is where it gets hard.

### Reproducibility

"A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" (reproducible-builds.org, Definitions). The build environment is named as an input. A build run inside a host app has that app's environment as part of its own.

## 2. How Substrate is built and run today

- `npm run pack:dev` builds `dist-electron/mac-arm64/Substrate.app` (runbook round 8, step 9). electron-builder fixes `appId` `com.greenrosesystems.substrate` and `productName` `Substrate` (`electron-builder.config.js` lines 46–47), and sets `buildVersion` to the build time in seconds (line 122).
- The bundle carries its own Python 3.14.4 and a kernel wheel built from `../substrate` HEAD (`scripts/fetch-python-runtime.sh`). Editing the kernel does not change an installed app.
- `electron/main.ts` line 290 names the app "Substrate Dev" when `SUBSTRATE_HOME` is set and "Substrate" otherwise. With `SUBSTRATE_HOME` set, `userData` and the logs move under `$SUBSTRATE_HOME/electron/` (lines 298–314). A packaged app opened from Finder gets no `SUBSTRATE_HOME`.
- The store is `Path(os.environ["SUBSTRATE_HOME"])` when set, else `~/.substrate` (`../substrate/src/substrate/home.py`).
- A session's `bash` runs `subprocess.Popen(..., shell=True, start_new_session=True)` with no `env` argument (`../substrate/src/substrate/topologies/tool_loop/tools.py` line 445). Every command a session runs inherits the backend's environment.
- The backend starts with `SUBSTRATE_PARENT_PID`, `SUBSTRATE_BOOT_ID`, `SUBSTRATE_TRACE_DIR` and, when packaged, `PYTHONHOME` (`electron/main.ts` lines 520–529).
- The gates launch Electron with their own `SUBSTRATE_HOME`, `--user-data-dir` and `SUBSTRATE_GATE_ISOLATE` (`harness/shakeout/lib/electron.ts` lines 39–49). Sprint 486 ran steps 10–16 against the new bundle while the installed app was open and then quit it at step 17. Those gates already run beside an open install.

## 3. Conflicts

Each heading says how the conflict is known.

**3.1 Same-named installs share one lock (seen on this machine).** `main.ts` line 746 calls `app.requestSingleInstanceLock()`; a launch that fails to get it calls `app.quit()` and the running instance takes its arguments (lines 747–759). The lock lives in the data folder: the installed app's `~/Library/Application Support/Substrate/` holds `SingletonLock`, `SingletonSocket` and `SingletonCookie`, and gates with their own `--user-data-dir` run beside the open install. Electron's `app` documentation does not say this; the evidence is the files and the gates. `userData` defaults to "the `appData` directory appended with your app's name" (Electron, `app.getPath`), so a second install also named Substrate gets the same folder, the same lock, and quits on launch.

**3.2 The install step quits the app doing the installing (read in the code).** Runbook step 17 runs `osascript -e 'tell application "Substrate" to quit'`. Step 18 moves `/Applications/Substrate.app` to the Trash. Run from a session in the working install, step 17 ends that session. Quitting also stops every running task in the session's task table (`server.py` `_shutdown_all_sessions` calls `TABLE.stop_all`; `background.py` line 224), so a script that a session starts in order to do the swap is stopped by the swap's own first step.

**3.3 A shared store: each backend ends the other's sessions (read in the code; not run).** At startup the session registry loads every manifest under the store (`session_registry.py` line 409). On quit, `_shutdown_all_sessions` (`server.py` lines 632–700) sends `SessionEndRequested(source="daemon_shutdown")` to every manifest it holds that is not `ended` or `interrupted`. Two backends on `~/.substrate` would therefore end each other's live sessions, and write into records the other backend has open. The registry's docstring says "the process-level lock lives at `~/.substrate/daemon.pid`" (line 299), but no code takes that lock and the file does not exist; nothing stops a second backend from starting on the same store. Logs collide the same way: both installs would write `~/Library/Logs/Substrate/substrate.log`.

**3.4 A test server run from a session writes into the working app's trace (measured).** `harness/shakeout/lib/server.ts` starts `server.py` with `...process.env` and sets `SUBSTRATE_HOME`, but leaves `SUBSTRATE_TRACE_DIR` and `SUBSTRATE_BOOT_ID` as inherited (lines 76–83). The server appends to `server.jsonl` in whatever folder `SUBSTRATE_TRACE_DIR` names (`server.py` lines 512–530). Run with both variables pointed at a scratch folder, as a session's `bash` would pass them, `npx tsx harness/vm_smoke.ts` passed 12 of 12 steps and wrote 6 records there, all with the inherited boot id, starting with `SERVER_STARTED` at `proc_seq` 0. In the working app's real trace that is a second server inside one boot. The vocabulary merges the trace "by boot_id, proc_seq and the causal keys", so the two servers' records collide on those keys. The test server also inherits `SUBSTRATE_PARENT_PID` and so exits when the working app exits (`server.py` lines 6934–6945); that side effect is harmless.

**3.5 Not conflicts.**

- `PYTHONHOME`. The packaged backend starts with `PYTHONHOME` set to its bundled library. A build's Python run with that value dies: `PYTHONHOME=/Applications/Substrate.app/Contents/Resources/python uv run --project ../substrate python -c "print(1)"` exits 1 with "Failed to import encodings module". The server clears the variable first thing (`release_python_home`, `../substrate/src/substrate/interpreter.py`, called at `server.py` line 6716, since commit ebb7b3a3 of 2026-10-13), so a session's commands never see it. `ps` still shows it on the backend, because `ps` prints the environment a process started with.
- The kernel. Each bundle carries its own; `../substrate` edits reach only the next build.
- The Electron gates. They set their own store, data folder and boot id.

## 4. Design

The test install is built from the same tree with a second `productName` and `appId`, and with its store fixed in the bundle rather than read from an environment variable, since Finder passes none. Its data folder, single-instance lock and log folder follow from the name; its store is a sibling of `~/.substrate`. The working install keeps today's identity, so its sessions and settings stay where they are. This is how Chrome Canary and VS Code Insiders sit beside their stable builds.

The runbook's steps 17–20 then install into the test install's bundle path and quit only the test install, by its own name. A session in the working install can run the whole runbook without ending itself.

Promoting a tested build into the working slot quits the working install, which ends its sessions with `daemon_shutdown` and stops every task a session started (3.2). The swap therefore runs as a job outside the app's task table and process group, handed to launchd: wait for the working app's pid to exit, move the old bundle to the Trash by version (step 18), copy the new one in (step 19), open it (step 20). The trashed bundle is stage 0: the runbook's rollback (section 5.2) restores it. Sessions continue through resume, which `resume_ended_session` already gates.

The promoted build's kernel reads records written by the old one: this is Fowler's database problem. Each record and the vocabulary carry versions (`APP_BOOTED.vocab_version`). Before promotion, the test install opens a copy of the working store's records and resumes one; that is the check that both builds can read the same data.

The two defects found here come first. The harness server sets its own `SUBSTRATE_TRACE_DIR` and `SUBSTRATE_BOOT_ID`, or clears them, so a test server cannot write into the working app's trace (3.4). The store takes the lock its docstring names, so a second backend on one store refuses to start instead of ending the first's sessions (3.3).

## 5. What this asks of SDD

The second build adds no new kind of event. It does add a second writer of the same vocabulary, and the trace has to tell the two writers apart.

`APP_BOOTED` carries `app_version`, `app_commit`, `kernel_commit`, `vocab_version`, `packaged`, `home_kind` and `gate_isolated`. Two packaged installs write the same values for all but the version fields. A `PAYLOAD_FIELD_PROPOSED` for the install's name lets a reader, and the Rubber Duck Pass, tell which app spoke. It is ratified, with a version bump, in the sprint that builds the identities.

Conflict 3.4 breaks the stated invariant that records merge "by boot_id, proc_seq". No new tag fixes that; the observation contract checks the fix.

The observation contract for the identities: with the working install open, the test install is built, installed and opened by the runbook from a session inside the working install. Afterwards: the working install's pid is unchanged; the two data folders each hold their own `SingletonLock`; the two stores hold disjoint session lists; the working app's `server.jsonl` holds one `SERVER_STARTED` for its boot. Real fixtures, a capable model for any live gate, screenshots read, mutants on each guard.

The cards, at most two files each, in this order: the harness server's trace variables; the store lock; the build identity and its store (electron-builder config and `main.ts`); the runbook round that installs into the test slot; the swap job. Each card follows the template.

## 6. Three experiments

**6.1 Diverse double-compiling, in Substrate's terms.** Build one commit twice: from a plain terminal, and from a session inside the working install. Normalize what is meant to differ (`buildVersion` is the build time, `electron-builder.config.js` line 122, and archives carry times) and compare the bundles file by file. Any remaining difference names something the host app leaked into the build. Conflict 3.4 was found by reading code; this comparison finds the leaks no one thought to read for. It is Wheeler's shape, with the plain terminal as the trusted second path.

**6.2 GCC's stage compare, as first proposed, does not hold here.** The chat reply before this paper proposed GCC's check: build B from inside A, build C from inside B, compare B with C. GCC's compare tests a compiler that compiles itself. Substrate does not compile Substrate: `tsc`, `vite`, electron-builder and `uv` do, and the app only hosts the shell that runs them. B against C would test the same environment leak as 6.1, with timestamps guaranteeing a difference. 6.1 is that test done properly; 6.2 is dropped.

**6.3 Gates against real use.** The working install's own trace records each day's work, for example `EDITOR_FILE_SHOWN` with its milliseconds. The same tags from the test install's gates give the build under test's numbers. Set side by side, the two show whether the gates exercise what the work exercises, with numbers only. Records from the machine stay out of the repo.

## 7. Pressure test of the chat reply that preceded this paper

| Claim in the reply | Finding |
|---|---|
| The lock "belongs to that name's data folder" | Holds; the evidence is the `Singleton*` files and the gates. Electron's documentation does not say it |
| Installing "would quit the build you're working in" | Holds, and goes further: the quit also stops every task the session started, so the session cannot run the swap itself |
| A shared store "could end or resume sessions" of the other build | Holds in the code, and goes further: the store lock named in `session_registry.py` does not exist |
| The kernel "isn't a conflict" | Holds for code; the records both kernels read are the shared data a swap must carry (Fowler) |
| The gates "aren't either" | Holds for the Electron gates; the harness server leaks trace variables (3.4, measured) |
| GCC's stage compare "could tell us something interesting" | Fails as stated (6.2); Wheeler's double build with a plain terminal (6.1) is the test that applies |
| "Eating our own dogfood" dates to a 1988 Microsoft email | Not rechecked here and not needed by the argument; left out |
