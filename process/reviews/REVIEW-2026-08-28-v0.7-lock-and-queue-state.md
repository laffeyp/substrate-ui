## What is off

### V1 — Ratification landed in `## Built`, not `## Decisions`. Same class the 2026-08-15 v0.1 halt named.

The BLACKBOARD entry for 032a lives at line 68, under `## Built`. Section-check via awk confirms it. AGENTS.md single-writer discipline (as amended 2026-07-22) allows any writer to record a made decision in `## Decisions`; a *vocabulary lock* is the canonical decision — the lock IS the contract, and the contract's ratification belongs in the section named for decisions.

The substrate-ui BLACKBOARD's own 2026-08-15 halt (F5, `awaiting_architect_decision: v0.1 lock has no ## Decisions entry`) named this exact class. The 2026-08-16 v0.2 lock closed the halt by writing to `## Decisions`. v0.7 backslides to the pre-halt shape.

`locked_by` prose in the JSON is not a substitute. The Architect's decision is the record's contract; `## Built` is a place for "here's what shipped," and a lock is not "shipped" the way a feature is — it is a ratified contract change.

**Fix.** One-line entry under `## Decisions`, dated 2026-08-28, naming v0.7 as the locked contract and pointing at the `## Built` entry for the full body. ~30 seconds of work.

### V2 — Dual-contract audit table implicit, not explicit.

BOOTSTRAP.md §Step 9 (Dual-Contract Audit) wants every behavior-category tag paired with either a view-category tag, a structural payload field on an existing view tag, or a typed gap-proposal. The five new `driver_session` (behavior) tags pair with: *manifest state on disk*, verified by 036a–e's per-control parity smoke and 036f's consolidated `test_ui_control_parity.py`.

That is a legitimate pairing shape — file-state-verifier as the observation-contract leg — but BOOTSTRAP.md does not enumerate it. The rationale doc names it in prose ("pair by construction with the manifest state their PATCH/POST writes"). What is missing: an explicit audit table row per new tag naming the exact manifest field the tag witnesses.

**Fix.** Append a `## Dual-contract audit table` section to `0.7-rationale.md`. Zero code change.

### V3 — `driver_session` category now spans two sources. Payload does not distinguish.

The `driver_session` category in v0.6 carries lifecycle tags projected from the substrate wire (the daemon's own record envelopes, mirrored to the UI). v0.7's five additions fire from a different source: the UI's own round-trip against a daemon endpoint. Same category, two distinct emission sources. The manifest state a tag witnesses is on disk (daemon-authoritative); the tag itself is UI-emitted.

For grader work: a source-agnostic reader cannot tell whether `DRIVER_PATCHED{session_id="s_...", driver="ollama:...", prior_driver="deterministic"}` came from the UI's PATCH round-trip or from a hypothetical future projector reading the same manifest change off the wire. Adding a `source: "ui_roundtrip" | "wire_projection"` optional payload field would close the ambiguity. Not urgent; texture.

**Fix (optional).** Add `source` as `optional_payload` on the five new tags in a hypothetical v0.7.1 or v0.8. Do not bump the current lock for this.

### V4 — 8 v0.6 tags locked with no known emit sites.

Parity gate reports 67/67 with 54 emit sites. Five of the 13 unemitted-but-locked tags are v0.7 additions (waiting on 034b + 036a–e). That accounts for 5 of 13. The other 8 are v0.6 tags with no current emit site.

Not a v0.7 defect; a v0.6 drift the v0.7 pass could have surfaced.

**Fix.** Drift-watchlist entry: "v0.7 parity reports 8 locked v0.6 tags with no emit sites (excluding 5 v0.7 additions waiting on their motivating sprints). Investigate whether speculative or dead." One BLACKBOARD line under `## Drift watchlist`.
