# v0.14 rationale — panes and the window's boot (sprint 360)

*Locked 2026-11-07. Supersedes `0.13.json`; still 88 tags. Plan `process/planning/2026-11-05-sdd-signals/`, item 4, panes and the window. Earlier rationales cover everything not named here.*

## The changes

Six proposals in `../proposals.json`, each read off `web/app/App.tsx` and `web/reveal.ts`.

**`P-0.14-PANE-OPENED`** (`PAYLOAD_FIELD_PROPOSED`). `PANE_OPENED.cause` loses `restore`. Panes are made only:
- at start: pane 1, or the layout's tweak props;
- by a split;
- by `openRunPanes`;
- by `openSessionPane`.

A reload reopens pane 1's session, not panes. That is a binding: `PANE_BOUND` how `restore`.

**`P-0.14-PANE-FOCUSED`** (`PAYLOAD_FIELD_PROPOSED`). `PANE_FOCUSED.cause` loses `key` and gains `close`. `web/app/keymap.ts` has no key that moves focus between panes. Closing a pane gives focus to its neighbour, which had no value.

**`P-0.14-PANE-BOUND`** (`PAYLOAD_FIELD_PROPOSED`). A pane is bound when it stops showing its picker. That is the test `computeViews` already draws by: the window marked the pane bound, or its controller holds a session.

`how` gains `direct`. Two paths bind a pane through its controller, outside the window's controls: ten gates do it through `window.__vm`, and so do the registry's calls. The reload's `?session=` goes through the controller too, from `web/reveal.ts`; the window notes it at mount as `restore`. A path the window does not note is written `direct`, so a window path that forgets its note shows up as `direct`. `pane_signals.ts` checks the picker's `picker`, and the plant that drops the note fails it.

**`P-0.14-PANE-CLOSED`** (`INVARIANT_PROPOSED`). `had_session` means the pane showed a session or record, by the same test. A run's pane holds a record and no session id.

**`P-0.14-WINDOW-BOOTED`** (`INVARIANT_PROPOSED`). `WINDOW_BOOTED` is written by the first statement of `web/reveal.ts` boot, before the pane registry exists. v0.7 placed it after App mounted, and pane 1's records could come first, against S1.

**`P-0.14-CONTEXT-PANE`** (`PAYLOAD_FIELD_PROPOSED`). The record context's `pane_id` is the pane the record is about. That covers a controller's own pane, and the pane a window component draws or changes. The eight `PICKER_*` emits wrote null there while their payloads named the pane, so a reader filtering a pane's records lost its picker steps. They now pass it.

## Where each is written

`App.tsx` compares each commit with the one before it (`componentDidUpdate`, `notePanes`), and pane 1's opening is written at mount. Where the state cannot say why, the path that made the change notes it first:
- a click, or a run or delegate path, for focus;
- the picker's commit, a session row, the records page or the reload, for binding.

Every other cause is read from the state:
- a new pane carries `runRoot` or `childSid`, or neither;
- focus that moves to a new pane is a split;
- focus that leaves a removed pane is a close.
